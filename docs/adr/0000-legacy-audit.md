# ADR-0000. Аудит legacy-коду (варіант 3, «Мережа фітнес-клубів»)

- **Статус:** прийнято
- **Дата:** 2026-10-28
- **Завдання ЛР:** 1
- **Об'єкт аналізу:** `src/main/java/variant3_fitnessmembership/*` (оригінальний код варіанта; класи лише рознесено по файлах, бо Java не дозволяє кілька `public`-класів в одному файлі)

## 1. Контекст

Система оформлює абонементи фітнес-клубу. Вона рахує ціну за типом пакета (Day / Full / VIP), застосовує дисконтну карту, додає первинні послуги (персональний тренер), формує текст договору, записує абонемент у БД і надсилає push-сповіщення.

У legacy-реалізації всі ці кроки виконує **один метод** `LegacyFitnessService.registerSubscriptionConsole()` (рядки 10–63, ≈ 55 рядків коду).

## 2. Виявлені проблеми

### 2.1. Анемічна доменна модель і порушення інкапсуляції

| #   | Де                                                     | Проблема                                                     | Наслідок                                                                                                                                                |
| --- | ------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | `Member`, `MembershipPlan`, `Subscription`             | Усі поля `public`, методів немає (Anemic Domain Model)       | Будь-який код може записати будь-що. Інваріанти ніде не захищені                                                                                        |
| A2  | `Subscription.baseAmount / discountAmount / finalCost` | Три незалежні `public double`-поля                           | Можна отримати `finalCost ≠ baseAmount − discountAmount`                                                                                                |
| A3  | `Subscription.status` (рядки 30, 52)                   | Статус — довільний `String` (`"Draft"`, `"Active"`)          | Опечатка `"Actve"` компілюється. Немає правил переходів (повторна активація, активація без розрахунку ціни)                                             |
| A4  | `Subscription.startDate = "2026-11-01"` (рядок 29)     | Дата як `String`                                             | Немає перевірки формату чи коректності дати                                                                                                             |
| A5  | рядки 18–30                                            | Об'єкти створюються через `new` + присвоєння полів по одному | Між рядками 24 і 51 абонемент перебуває в невалідному стані (ціни 0, статус `Draft`). Немає жодної перевірки (порожнє ім'я, від'ємна ставка, 0 місяців) |

### 2.2. «Спагеті-код» і Bloated Controller / Monolithic Main

Метод `registerSubscriptionConsole()` має **7 різних обов'язків** (порушення SRP і High Cohesion):

| #   | Обов'язок                                                                | Рядки |
| --- | ------------------------------------------------------------------------ | ----- |
| 1   | Консольний ввід/вивід (`Scanner`, `System.out`)                          | 11–16 |
| 2   | Конструювання агрегату (Member, Plan, Subscription) з «магічними» даними | 18–30 |
| 3   | Тарифне ціноутворення (`if VIP … else if Day`)                           | 32–38 |
| 4   | Додаткові послуги (тренер +3000)                                         | 40–42 |
| 5   | Розрахунок знижки та підсумку, зміна статусу                             | 44–52 |
| 6   | Форматування тексту договору                                             | 54–59 |
| 7   | Інфраструктура: «запис у БД» і push-сповіщення                           | 61–62 |

Через це метод неможливо протестувати без підміни `System.in/System.out`, а будь-яка зміна (новий тариф, інша знижка, реальна БД) змушує редагувати той самий метод.

### 2.3. Порушення Information Expert і Закону Деметри

- Ціну рахує сервіс, хоча всі дані для цього належать `MembershipPlan` (ставка, місяці, тип) і `Subscription` (тариф, послуги).
- Ланцюжки звернень `sub.plan.baseMonthlyRate`, `sub.plan.monthsDuration`, `sub.plan.code`, `sub.member.hasDiscountCard`, `sub.member.name` (рядки 32–62) порушують Закон Деметри: сервіс «лізе» крізь `Subscription` у її внутрішні об'єкти.

### 2.4. Умовні розгалуження за типом (порушення Polymorphism / OCP)

```java
if ("VIP".equalsIgnoreCase(sub.plan.code)) { rawCost += 5000.0; }
else if ("Day".equalsIgnoreCase(sub.plan.code)) { rawCost *= 0.8; }
```

- Додати тариф «Student» можна лише новою гілкою в тому самому методі.
- **Прихований дефект:** невідомий код (`"Gold"`, `"vjp"`) мовчки рахується як Full, і користувач отримує договір на неіснуючий тариф. Це підтверджено характеризаційним тестом `LegacyEquivalenceTest.unknownPlanIsNowRejectedInsteadOfSilentlyChargedAsFull`.

### 2.5. Надмірне зчеплення (High Coupling) і «магічні» значення

- Сервіс напряму залежить від консолі (`Scanner`, `PrintStream`, `InputStream`), від трьох доменних класів і **неявно** від БД та push-сервісу (жорстко «вшиті» `System.out.println`). Виміряне CBO = 6, логічне (з прихованими БД і push) — 8.
- Бізнес-константи розкидані по коду: 1200.0, 12, 5000.0, 0.8, 3000.0, 0.10, 42, 1002, `"+380509998877"`, `"2026-11-01"`. Зміна ціни означає зміну коду бізнес-логіки.
- Гроші зберігаються в `double`, тобто в двійковій арифметиці з плаваючою комою. Наприклад, `1199.99 * 12 = 14399.880000000001` (див. ADR-0004).

## 3. Рішення

Переходимо до **Rich Domain Model** і багатошарової архітектури `cli → application → domain ← infrastructure`, застосовуючи 9 патернів GRASP. Детальні рішення з альтернативами (QOC) і компромісами:

| ADR                                             | Тема                                                   | Патерни GRASP                                |
| ----------------------------------------------- | ------------------------------------------------------ | -------------------------------------------- |
| [ADR-0001](0001-rich-domain-model.md)           | Багата доменна модель, фабричні методи                 | Information Expert, Creator                  |
| [ADR-0002](0002-thin-controller-and-ports.md)   | Тонкий CLI, Use-Case Controller, порти, технічні класи | Controller, Indirection, Pure Fabrication    |
| [ADR-0003](0003-pricing-polymorphism.md)        | Стратегії тарифів і знижок                             | Polymorphism, Protected Variations           |

Low Coupling і High Cohesion перевіряються кількісно: [docs/metrics/metrics-report.md](../metrics/metrics-report.md).

## 4. Наслідки

- Поведінку legacy-коду зафіксовано характеризаційними тестами (`LegacyEquivalenceTest`): суми для Day/Full/VIP збігаються до копійки.
- Legacy-код залишено в репозиторії як еталон «до» для тестів і метрик.
