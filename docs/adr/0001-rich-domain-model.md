# ADR-0001. Багата доменна модель: Information Expert + Creator

- **Статус:** прийнято
- **Дата:** 2026-10-28
- **Завдання ЛР:** 2
- **Пов'язані:** ADR-0000 (проблеми A1–A5, 2.3)

## Контекст

У legacy-коді сутності `Member`, `MembershipPlan` і `Subscription` — пасивні «мішки з даними», а вся логіка розрахунку живе в сервісі. Об'єкти збираються через `new` і присвоєння полів по одному, тому довгий час перебувають у невалідному стані.

## QOC 1. Хто має рахувати вартість абонемента?

**Question:** якому класу доручити розрахунок базової вартості, знижки й підсумку?

| Options \ Criteria | C1. Інкапсуляція інваріантів | C2. Тестованість | C3. Зчеплення сервісу | C4. Простота |
|---|---|---|---|---|
| O1. Залишити в сервісі (`PriceCalculatorService`) | − дані відкриті | ± | − сервіс знає про всі поля | + |
| O2. **`MembershipPlan.termPrice()` + `Subscription.open()` рахує `PriceBreakdown`** | + ціна недоступна для зміни ззовні | + юніт-тести без моків | + сервіс не знає формули | ± |
| O3. Окремий доменний сервіс `PricingService` (DDD) | ± | + | ± | − ще один клас без власних даних |

**Рішення: O2 (Information Expert).** Обов'язок отримує той, хто має потрібні дані:
- `MembershipPlan` знає ставку, кількість місяців і своє правило ціноутворення, тому сам рахує `termPrice()`;
- `Subscription` знає тариф, послуги й клієнта, тому сам формує `PriceBreakdown` під час створення;
- `DiscountCardPolicy` питає в `Member` лише `hasDiscountCard()` («tell, don't ask»: політика не лізе в поля клієнта).
- `PriceBreakdown` — незмінний `record`, інваріант `finalCost = baseAmount − discountAmount` перевіряється в конструкторі.
- `Subscription.activate()` інкапсулює правило переходу `DRAFT → ACTIVE`. Повторна активація кидає `IllegalStateException`.

**Компроміс:** O3 був би доречний, якби ціна залежала від кількох агрегатів (наприклад, від історії відвідувань). Поки всі дані в межах агрегату `Subscription`, окремий сервіс тільки збільшив би зчеплення.

## QOC 2. Як гарантувати створення об'єктів у валідному стані?

**Question:** як створювати `Member`, `MembershipPlan` і `Subscription`, щоб невалідний об'єкт не міг існувати?

| Options \ Criteria | C1. Валідність після створення | C2. Читабельність | C3. Незмінність | C4. Відповідність GRASP Creator |
|---|---|---|---|---|
| O1. Публічний конструктор без перевірок + сеттери (як у legacy) | − | ± | − | − |
| O2. Builder | ± (перевірка лише в `build()`) | + для багатьох полів | + | ± |
| O3. **Приватний конструктор + статичний фабричний метод із валідацією; агрегат створює свої частини** | + | + інтенційні імена `register`, `open`, `subscribe` | + `final`-поля | + |

**Рішення: O3 (Creator + Static Factory Method).**
- `Member.register(...)` перевіряє ім'я й телефон і нормалізує їх.
- `MembershipPlan.of(...)` перевіряє, що ставка > 0 і місяців > 0.
- `Subscription.open(...)` перевіряє id і null-аргументи, забороняє дублікати послуг, одразу рахує ціну й ставить статус `DRAFT`.
- **Creator за GRASP:** `SubscriptionOffer` (тариф + послуги + політика знижок) містить усі ініціалізуючі дані абонемента, тому саме вона його створює: `offer.subscribe(id, member, startDate)`. `Subscription` агрегує `PriceBreakdown` і сама його створює.
- Колекції захищені: `List.copyOf(addOns)` дає захисну незмінну копію, і `subscription.addOns().add(...)` кидає `UnsupportedOperationException`.

**Компроміс:** конструктор приватний, тож для тестів доводиться передавати повний набір валідних аргументів. Це свідома ціна гарантії валідності.

## Наслідки

- Сеттерів немає. Змінне поле тільки одне (`status`), і змінюється воно лише бізнес-методом `activate()`.
- `Money` (`record` на `BigDecimal`) — Value Object замість `double` (див. ADR-0004).
- LCOM4 ключових доменних класів = 1 (див. звіт метрик).
