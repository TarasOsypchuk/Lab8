# ADR-0004. Гроші в `BigDecimal`, валідація вводу, свідомі зміни поведінки

- **Статус:** прийнято
- **Дата:** 2026-10-28
- **Завдання ЛР:** 1–4 (наскрізне рішення)

## Контекст

Рефакторинг за визначенням не змінює поведінку. Проте частина поведінки legacy-коду є дефектами. Ці зміни фіксуємо явно, щоб їх можна було обговорити на захисті й під час рев'ю.

## QOC. Як представити гроші?

| Options \ Criteria | C1. Точність | C2. Безпека типів | C3. Простота |
|---|---|---|---|
| O1. `double` (legacy) | − `1199.99 * 12 = 14399.880000000001` | − гроші = будь-яке число | + |
| O2. `long` копійок | + | − | ± |
| O3. **`record Money(BigDecimal)`, scale 2, HALF_UP** | + | + окремий тип | ± |

**Рішення: O3.** Для поточних тарифів legacy-суми збігаються з новими до копійки (`LegacyEquivalenceTest`). `double` усе одно прибрано, бо ставка на кшталт 1199.99 дала б похибку.

## Свідомі зміни поведінки порівняно з legacy

| # | Legacy | Після рефакторингу | Обґрунтування |
|---|---|---|---|
| B1 | Невідомий тариф (`"Gold"`) мовчки рахується як Full | `IllegalArgumentException`: «Невідомий тип абонемента», абонемент не створюється | Інакше клієнт отримує договір на неіснуючий тариф. Тест `unknownPlanIsNowRejectedInsteadOfSilentlyChargedAsFull` |
| B2 | Порожнє ім'я приймається | Помилка валідації `Member.register` | Інваріант сутності |
| B3 | Телефон, дисконтна карта, тренер, дата, id «вшиті» в код | Вводяться користувачем або генеруються (`IntSupplier`) | Інакше система некорисна. Значення за замовчуванням legacy відтворено в характеризаційному тесті |
| B4 | Суми виводяться як `22400.0` | `22400.00` (2 знаки) | Грошовий формат |
| B5 | Статус `"Draft"` → `"Active"` без правил | `DRAFT → ACTIVE` лише через `activate()`, повторна активація заборонена | Стан захищено |

## Наслідки

Характеризаційні тести перевіряють, що для всіх валідних тарифів (`Day`, `Full`, `VIP`, `vip`, `day`) базова вартість, знижка й підсумок збігаються з legacy-кодом. Відмінності B1–B5 покриті окремими тестами.
