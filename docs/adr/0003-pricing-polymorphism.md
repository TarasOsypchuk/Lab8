# ADR-0003. Стратегії тарифів і знижок: Polymorphism + Protected Variations

- **Статус:** прийнято
- **Дата:** 2026-10-28
- **Завдання ЛР:** 4
- **Пов'язані:** ADR-0000 (п. 2.4, 2.5)

## Контекст

```java
if ("VIP".equalsIgnoreCase(sub.plan.code))      rawCost += 5000.0;
else if ("Day".equalsIgnoreCase(sub.plan.code)) rawCost *= 0.8;
...
if (sub.member.hasDiscountCard) discount = sub.baseAmount * 0.10;
```

Поведінка залежить від рядкового коду типу. Точки нестабільності: тарифні правила (з'являються нові пакети), правила знижок (акції, лояльність), сховище даних, зовнішній push-API.

## QOC 1. Як позбутися `if/else` за типом тарифу?

**Question:** як реалізувати відмінності між Day, Full і VIP?

| Options \ Criteria                                                                                    | C1. Додавання нового тарифу без змін існуючого коду (OCP) | C2. Налаштовуваність цін без перекомпіляції домену | C3. Простота | C4. Тестованість         |
| ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | -------------------------------------------------- | ------------ | ------------------------ |
| O1. `switch` по `enum PlanType`                                                                       | −                                                         | −                                                  | +            | ±                        |
| O2. `enum` з абстрактним методом (constant-specific body)                                             | − новий тариф = зміна enum                                | − числа вшиті в enum                               | +            | +                        |
| O3. Підкласи `DayPlan extends MembershipPlan`…                                                        | ±                                                         | −                                                  | ±            | ± наслідування сутностей |
| O4. **Інтерфейс-стратегія `PlanPricing` + параметризовані реалізації, композиція в `MembershipPlan`** | + новий клас або лямбда                                   | + коефіцієнт і надбавка — параметри                | ±            | +                        |

**Рішення: O4 (Polymorphism).**

| Тариф | Стратегія           | Параметр   |
| ----- | ------------------- | ---------- |
| Full  | `RegularPricing`    | —          |
| Day   | `MultiplierPricing` | `0.80`     |
| VIP   | `SurchargePricing`  | `5000 грн` |

`MembershipPlan.termPrice()` викликає `pricing.apply(monthlyRate × months)` і не знає, який саме це тариф. Тест `MembershipPlanTest.newPlanNeedsOnlyNewStrategy` показує, що «Студентський» тариф (×0.5) додається без жодної зміни в `MembershipPlan`, `Subscription` чи контролері.

**Компроміс:** O2 простіший, але кожен новий тариф змінював би enum, і числа знову опинилися б у домені. Композицію обрано замість наслідування (O3), бо тариф — дані з поведінкою, а не окремий тип сутності.

## QOC 2. Які точки нестабільності сховати за стабільними контрактами (Protected Variations)?

| Точка нестабільності | Стабільний контракт      | Поточна реалізація                            | Можлива заміна                                     |
| -------------------- | ------------------------ | --------------------------------------------- | -------------------------------------------------- |
| Алгоритм тарифу      | `PlanPricing`            | Regular / Multiplier / Surcharge              | сезонні, погодинні тарифи                          |
| Правила знижок       | `DiscountPolicy`         | `DiscountCardPolicy(10%)`, `NoDiscountPolicy` | програма лояльності, промокоди, комбінація політик |
| Каталог тарифів      | `TariffCatalog`          | `InMemoryTariffCatalog` + `DefaultTariffs`    | читання з БД/JSON, адмін-панель                    |
| Сховище              | `SubscriptionRepository` | `InMemorySubscriptionRepository`              | JDBC / JPA                                         |
| Зовнішній push-API   | `SubscriptionNotifier`   | `ConsolePushNotifier`                         | Firebase, SMS, email                               |
| Термінал             | `Console`                | `SystemConsole`                               | GUI, тестова консоль                               |
| Час                  | `java.time.Clock`        | `Clock.systemDefaultZone()`                   | `Clock.fixed` у тестах                             |

**Альтернатива, яку відкинули:** «захищати все» (інтерфейс на кожен клас). Це спекулятивне узагальнення (YAGNI). Інтерфейси введено лише там, де зміна реалістична або де без інтерфейсу не протестувати.

## Наслідки

- У домені й контролері немає жодного `if` за кодом тарифу. Пошук тарифу виконує `Map` у каталозі, нечутливий до регістру, як `equalsIgnoreCase` у legacy.
- Усі «магічні» числа зібрані в одному конфігураційному класі `DefaultTariffs`.
